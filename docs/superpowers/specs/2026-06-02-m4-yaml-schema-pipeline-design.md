# Mondrian-4 YAML Schema Pipeline — Design

**Date:** 2026-06-02
**Issue series:** #34 (YAML schema support)
**Branch:** `feature/34-m4-yaml-schema-pipeline`
**Status:** Approved design — pending spec review

## Problem

The YAML schema feature (#34) was built entirely around the **Mondrian-3 (M3)
legacy** schema vocabulary (`Dimension` / `Hierarchy` / `Level` /
`DimensionUsage` / `VirtualCube` / `Join`). The project is now **Mondrian-4
(M4) only**, and the canonical schema `demo/FoodMart.mondrian.xml` uses the M4
vocabulary (`PhysicalSchema` tables/columns/keys/links, attribute-based
`Dimensions`, `MeasureGroups`, `DimensionLinks`).

Evidence the current pipeline is M3-only:
- `XmlSchemaToYaml` reads only M3 tags. Running `to-yaml` on the M4 FoodMart
  produces a near-empty 56-line YAML from a 982-line schema (~94% data loss);
  the M3 FoodMart3 produces a faithful 1075-line YAML.
- `YamlSchemaConverter` Javadoc explicitly lists `MeasureGroup` as **out of
  scope**.
- `SchemaCli.lint` only *detects* M3-vs-M4 (to decide whether to run modern XSD
  validation); it never converts M4.

We need: a real, committed YAML version of the M4 FoodMart schema that loads as
a first-class catalog and is proven equivalent against the FoodMart test
dataset — and the converter machinery to support M4 generally.

## Goals

1. Full M4 support in the YAML converter pipeline (both directions).
2. Keep the existing M3 pipeline working (dual-vocabulary support).
3. Commit `demo/FoodMart.yaml` (M4) and validate it against the FoodMart
   dataset via the existing SmokeCorpus 20-query equivalence harness.

## Non-goals

- Removing or rewriting the M3 pipeline. M3 stays as-is.
- Changing the Mondrian runtime/loader. M4 XML already loads; we only produce
  it.
- A new YAML parser/emitter library. Reuse whatever the M3 path uses.

## Key decisions (agreed)

| Decision | Choice |
|---|---|
| Converter architecture | Pivot M4 to the typed `MondrianDef` (XOM) object graph ↔ YAML |
| M3 disposition | Keep M3 working alongside M4 (converters become dispatchers) |
| Delivery | Phased: physical → dims/attrs → measure groups → roles/calc → FoodMart capstone |
| Source schema | `demo/FoodMart.mondrian.xml` (M4 modern) |
| YAML production | Generate via converter, commit the output |
| Validation | Reuse the SmokeCorpus 20-query harness against the committed YAML file |

## Why MondrianDef/XOM

`MondrianDef` (generated by XOM from the M4 model — 85 typed element classes) is
the Mondrian-4 model. XOM gives M4 XML I/O for free:
- **XML → object graph:** `new MondrianDef.Schema(domWrapper)` (exactly what
  `RolapSchemaLoader` does at `RolapSchemaLoader.java:295`).
- **object graph → XML:** every `ElementDef` has `displayXML(...)`.

So the M4 converter only has to map `MondrianDef` ↔ YAML; all XML
parsing/serialization is delegated to XOM. This avoids hand-rolling fragile
DOM/string handling for 85 element types.

## Architecture & module layout

The two public converter classes become **vocabulary dispatchers**; M4 logic
lives in a new sub-package for cohesion.

```
mondrian.schema.yaml
  XmlSchemaToYaml      (existing) toYaml(xml): detect vocab → M3 or M4 ingest
  YamlSchemaConverter  (existing) toXml(yaml): detect flavour → M3 or M4 emit
  SchemaCli            (existing) extend to-yaml/to-xml/lint for M4
  m4/
    M4XmlToYaml        new: MondrianDef.Schema → YAML
    M4YamlToXml        new: YAML → MondrianDef.Schema → displayXML() → XML
    (helpers as needed, kept small/focused: physical, dimensions, measure groups)
```

- Ingest dispatch reuses the `hasMondrian4Elements` logic currently in
  `SchemaCli` (presence of `<PhysicalSchema>` child or any
  `<Cube><MeasureGroups>` grandchild). Extract it to a shared helper.
- Emit dispatch routes on YAML flavour: explicit `schema.metamodel_version:
  "4.0"`; fallback structural (presence of `physical_schema` / `measure_groups`).
  M3 YAML keeps its current scalar `schema: "FoodMart"` top key; M4 uses a
  `schema:` mapping — so the two are structurally unambiguous.

## M4 YAML shape

Idiomatic YAML mirroring the M4 model. Key-naming convention: `snake_case` keys,
XML attribute names mapped to snake_case (e.g. `formatString` → `format_string`,
`hasHierarchy` → `has_hierarchy`, `allMemberName` → `all_member_name`).

```yaml
schema:
  name: FoodMart
  metamodel_version: "4.0"

physical_schema:
  tables:
    - name: salary
    - name: salary
      alias: salary2
    - name: department
      key: [department_id]
    - name: product
      key_column: product_id          # attribute form of single-column key
    - name: customer
      key: [customer_id]
      calculated_columns:
        - name: full_name
          type: String
          expression:                 # SQL-by-dialect, preserved verbatim
            oracle: "{fname} || ' ' || {lname}"
            mysql:  "CONCAT({fname}, ' ', {lname})"
            generic: "{fullname}"
  links:
    - {source: employee,      target: employee_closure, foreign_key: [employee_id]}
    - {source: product_class, target: product,          foreign_key: [product_class_id]}

shared_dimensions:
  Store:
    table: store
    key: Store Id
    attributes:
      - {name: Store Country, has_hierarchy: false, key: [store_country]}
      - {name: Store State,   has_hierarchy: false, key_column: store_state}
      - name: Store City
        has_hierarchy: false
        key:  [store_state, store_city]
        name_column: store_city
      - name: Store Name
        key_column: store_name
        has_hierarchy: false
        properties: [Store Type, Store Manager, Store Sqft]
      - {name: Store Type, key_column: store_type, hierarchy_all_member_name: All Store Types}
    hierarchies:
      - name: Stores
        all_member_name: All Stores
        levels: [Store Country, Store State, Store City, Store Name]
      - name: Store Size in SQFT
        levels: [Store Sqft]

cubes:
  Sales:
    default_measure: Unit Sales
    annotations:
      caption.de_DE: Verkaufen
    dimensions:
      - {source: Store}               # usage of a shared dimension
      - {source: Time}
      # cube-local dimensions inline with the same shape as shared_dimensions
    measure_groups:
      - name: Sales
        table: sales_fact_1997
        measures:
          - {name: Unit Sales,    column: unit_sales, aggregator: sum, format_string: Standard}
          - {name: Customer Count, column: customer_id, aggregator: distinct-count, format_string: "#,###"}
        dimension_links:
          - {type: foreign_key, dimension: Store,   foreign_key_column: store_id}
          - {type: foreign_key, dimension: Time,    foreign_key_column: time_id}
      - table: agg_c_special_sales_fact_1997
        type: aggregate
        measures:
          - {ref: Fact Count, agg_column: fact_count}
          - {ref: Unit Sales, agg_column: unit_sales_sum}
        dimension_links:
          - {type: foreign_key, dimension: Store, foreign_key_column: store_id}
          - {type: copy,        dimension: Time,  attribute: Month}
    calculated_members:
      - name: Profit
        dimension: Measures
        formula: "[Measures].[Store Sales] - [Measures].[Store Cost]"
        properties: [{name: format_string, value: "$#,##0.00"}]

roles:
  - name: California manager
    schema_grant:
      access: none
      cubes:
        - {cube: Sales, access: all, hierarchies: [...]}   # reuse existing grant shape
```

Final key names are pinned during Phase 1 implementation and documented in the
user guide update. The `dimension_links` `type` enum: `foreign_key`, `copy`,
`no_link`, `fact` (fact link). Single-column keys may use `key_column: X`;
multi-column use `key: [A, B]`. `Name`/`OrderBy`/key expressions with SQL
dialect blocks use the same `expression: {dialect: sql}` shape as calculated
columns.

## Component contracts

- **`M4XmlToYaml.toYaml(MondrianDef.Schema) : String`** — pure function over the
  typed graph; no DOM. Depends on the YAML emitter + the M4 model.
- **`M4YamlToXml.toXml(String yaml) : String`** — parse YAML → build
  `MondrianDef.Schema` → `displayXML()`. Depends on the YAML parser + the M4
  model. Fallback: where programmatic graph construction is awkward for a
  specific element, emit that element's M4 XML from a small template; default is
  the typed graph.
- **Dispatchers** — `XmlSchemaToYaml.toYaml` / `YamlSchemaConverter.toXml`
  unchanged signatures; add internal routing. No behaviour change for M3 input.

## Data flow

Ingest: `M4 XML → XOM parse → MondrianDef.Schema → M4XmlToYaml → YAML`.
Emit:   `YAML → M4YamlToXml → MondrianDef.Schema → displayXML() → M4 XML →
RolapSchemaLoader (unchanged)`.

## Error handling

- Unknown YAML keys → fail fast with a clear path-qualified message (e.g.
  `cubes.Sales.measure_groups[1]: unknown key 'aggcolumn' (did you mean
  'agg_column'?)`). Validate at the YAML boundary; never silently drop.
- Unsupported/edge M4 elements encountered during ingest → fail loudly listing
  the element, rather than emitting lossy YAML (the exact trap that hid this
  problem originally).
- `to-xml` output is structurally validated by constructing
  `MondrianDef.Schema`; `lint` additionally runs the modern XSD path for M4.

## Testing strategy

Per phase: an XML→YAML→XML **MDX-equivalence** test on the real FoodMart dataset
covering that phase's elements (assert byte-identical cells vs the original M4
XML). Mirrors the existing `FoodMart3MdxEquivalenceTest` pattern but on M4.

Capstone:
- Commit `demo/FoodMart.yaml` (generated by the M4 converter from
  `demo/FoodMart.mondrian.xml`).
- New `FoodMartYamlSmokeCorpusEquivalenceTest`: load the **committed YAML file**
  as a first-class catalog and `demo/FoodMart.mondrian.xml`, run
  `SmokeCorpus.queries()` (20) against both, assert 0 divergent queries (same
  skip-if-XML-baseline-fails logic as the M3 version).
- A **drift guard**: regenerate YAML from the XML in-test and assert it equals
  the committed `demo/FoodMart.yaml`, so the committed artifact can't silently
  drift from the schema.

Regression: all existing M3 `FoodMart3*` and `YamlSchema*` tests stay green
(proves dual-vocabulary support intact).

## Phasing

1. **Physical layer** — `PhysicalSchema`: tables, keys (`Key`/`keyColumn`),
   columns, `Link`/`ForeignKey`, `ColumnDefs`/`CalculatedColumnDef` with SQL
   dialect blocks, inline tables. Dispatch scaffolding + detection helper
   extracted. Phase test: physical round-trip + a query that uses the calculated
   `full_name` column.
2. **Dimensions/attributes** — attribute-based `Dimensions`/`Dimension`,
   `Attributes`/`Attribute` (key/name/order expressions, properties,
   `has_hierarchy`, all-member naming), `Hierarchies`/`Hierarchy`/`Level`
   over attributes. Phase test: Store + Time multi-hierarchy equivalence.
3. **Measure groups** — `MeasureGroups`/`MeasureGroup` (`type`), `Measures`,
   `Measure`, `MeasureRef`, aggregators, `DimensionLinks`
   (`ForeignKeyLink`/`CopyLink`/`NoLink`/fact), `AggTable` fidelity. Phase test:
   Sales measures + agg-table equivalence.
4. **Roles & calc** — `CalculatedMembers`/`CalculatedMember`/`Formula`/
   `CalculatedMemberProperty`, `NamedSets`, `Roles`/grants, `Annotations`.
   Phase test: calc-member + role-restricted query equivalence.
5. **Capstone** — generate + commit `demo/FoodMart.yaml`; wire
   `FoodMartYamlSmokeCorpusEquivalenceTest` + drift guard; `lint` clean; update
   `SchemaCli`/wrapper docs and the #34 user guide.

Each phase is independently reviewable and leaves the build green.

## Open risks & mitigations

- **Programmatic `MondrianDef` graph construction (emit) is the hardest half.**
  Mitigation: templated-XML fallback per stubborn element; the typed graph
  remains the default.
- **`metamodelVersion='4.0'` and agg-table fidelity must survive round-trip.**
  Mitigation: explicit assertions in phase tests; drift guard at capstone.
- **FoodMart M4 may use features the HSQLDB FoodMart dataset doesn't fully
  exercise.** Mitigation: SmokeCorpus harness already skips queries the XML
  baseline can't run — only YAML-vs-XML divergence counts.
- **YAML key bikeshedding.** Mitigation: pin the full key vocabulary in Phase 1,
  document it once, reuse thereafter.
